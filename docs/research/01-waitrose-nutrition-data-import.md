# Research digest (2026-10-25)

Output of six parallel research agents. Vendor sites were blocked from the sandbox, so some figures are flagged "verify live". Treat URLs as leads, not citations.


########## waitrose-pricing ########## findings: 27

--- SUMMARY ---
Waitrose has no public or developer API; every "Waitrose API" on the market is a third-party scraper. The site's real backend is well understood from open-source clients (npm `waitrose` 1.2.2, last published 2026-10-05, vendored into `LionZXY/waitrose-mcp`): a GraphQL endpoint at `POST https://www.waitrose.com/api/graphql-prod/graph/live` (login, trolley, orders, slots; introspection disabled) plus REST services under `www.waitrose.com/api/<service>-prod/...`, of which product search (`content-prod/v2/cms/publish/productcontent/search/-1?clientType=WEB_APP`) and product lookup by line number (`products-prod/v1/products/{lineNumbers}?view=EXTENDED`) work anonymously with `Authorization: Bearer unauthenticated`. The host `api.waitrose.com` named in the brief does not appear in any client; everything is on `www.waitrose.com/api/`. Search responses carry price (`displayPrice`, `currentSaleUnitPrice{price{amount,currencyCode},quantity}`, `displayPriceQualifier`), `promotions[]` (incl. `myWaitrosePromotion`, `promotionExpiryDate`), `size`, images and `isHfss`, but no nutrition or allergen fields; those live only on product pages. Login is effectively closed to automation: Akamai's "I'm not a robot" challenge on `auth.waitrose.com` blocked both headless and headed login as of 2026-10-06, so order history and favourites cannot be pulled server-side; Waitrose offers no order/favourites CSV export, only "Order Details"/receipt emails and GDPR rights requests. robots.txt (header dated 2011) sets `Crawl-delay: 1` and disallows trolley, checkout and the token-auth API path; the site T&Cs state that no part of the website may be reproduced without written permission, and vendors report Akamai bot management plus non-UK IP blocking, so a Vercel (AWS datacenter IP) backend hitting these endpoints is both a ToS breach and likely to be blocked intermittently. No open dataset includes Waitrose: Open Prices (ODbL, anonymous REST API with `product_code`/`location_osm_id`/`currency` filters) has negligible UK/Waitrose coverage, the free CC-BY-4.0 Apify UK dataset covers Tesco/Sainsbury's/Asda/Aldi only, and the Kaggle UK time series is ~2.5 years stale and excludes Waitrose; paid scrapers (Apify $0.40-$5 per 1k results, Bright Data, Channel3 1,000 free calls/month) exist but merely outsource the same scraping. Competitors confirm there is no shortcut: Samsung Food's UK integrations are Tesco and Ocado via retailer-provided catalogue mapping and SSO/redirect, Jow is France/US only, and Mealime has no UK retailer link. The robust design is therefore a per-ingredient "price memory" with explicit staleness, fed by (in order) user-pasted Waitrose product URLs/basket text, forwarded order emails extracted by Claude, and an optional browser extension running in the user's own logged-in waitrose.com session; a direct server-side call from Vercel `lhr1` should at most be a feature-flagged, cached, rate-limited best-effort refresh that the UI never depends on.

--- RECOMMENDATION ---
1) Build the pricing layer around a first-class `PriceObservation` table, not a live feed: {ingredient_id, retailer:'waitrose', product_ref (6-digit lineNumber string, nullable), product_name, pack_size, pack_price_pence, unit_price_pence, unit_uom, promo{description, expiry, myWaitrose:boolean}|null, source: 'manual'|'url_paste'|'order_email'|'extension'|'api', observed_at}. Every shopping-list total is computed from the latest observation per ingredient and is always labelled an estimate. 2) Ship these inputs first, all robust from Vercel: (a) manual entry/edit of price per ingredient; (b) paste of Waitrose product URLs (regex the lineNumber from /ecom/products/<slug>/<6digits>-...) and of free-text basket/receipt text, with Claude extracting name, size, price, unit price; (c) forward the Waitrose 'Order Details'/receipt email to an inbound address (e.g. Resend/Postmark inbound webhook) and have Claude extract line items -> observations; this also learns what the user actually buys. 3) Second phase: a tiny browser extension or bookmarklet that runs inside the user's own logged-in waitrose.com tab (same-origin, Akamai cookies already valid), reads product tiles/trolley or calls the page's own JSON endpoints, and POSTs observations to the app. This is the only way to get trolley/favourites/order data given the Akamai login challenge, and it avoids any server-side automated access. 4) Optional, feature-flagged, off by default: a server-side 'refresh' job from Vercel region lhr1 that calls GET https://www.waitrose.com/api/products-prod/v1/products/{lineNumbers joined by '+'}?view=EXTENDED&excludeLinesWithConflicts=false&filterByCustomerSlot=false with headers Accept: application/json, User-Agent 'Waitrose/3.9.1 (Android)', Authorization: Bearer unauthenticated, batching up to ~20 line numbers per call, max 1 request/second (robots Crawl-delay 1), at most once per 24 h per product, with a circuit breaker on any 403/timeout/HTML body and no retries. Treat it as a breach-prone convenience that may stop at any time; never store Waitrose credentials server-side; do not use it in a multi-user hosted product. Do not pay for Apify/Bright Data/Channel3 scrapers for a household app; they cost money for the same ToS exposure. 5) Staleness policy: observed_at < 7 days = fresh (normal weight); 7-30 days = 'approx' (muted colour, ~ prefix); 30-90 days = stale (grey, flagged in list header 'k of n prices older than a month'); > 90 days = excluded from the total and prompts re-confirmation; promotions are dropped at promotionExpiryDate and the base price is shown instead; show the basket total as a range (promo-inclusive low to regular-price high) and a coverage count ('priced 23 of 27 items'). 6) Product matching: store one preferred Waitrose product per ingredient (lineNumber + pack size + unit price) chosen by the user from search or pasted; compute recipe cost as max(1, ceil(required_qty/pack_size)) packs for pantry-style items and unit-price * quantity for loose/weight items using currentSaleUnitPrice and displayPriceQualifier. 7) Nutrition does not come from Waitrose price data; source it from Open Food Facts (ODbL, ~2,700 Waitrose own-brand products) or a nutrition database and keep it decoupled from pricing. 8) Reverse direction is free: generate a plain-text list for Waitrose's Multi-search box (one item per line, keep under 50 to be safe) so the user builds the trolley in seconds.

########## nutrition-data ########## findings: 49

--- SUMMARY ---
The right backbone for a UK household app is McCance & Widdowson's CoFID: the latest edition is still 2021 (no 2022-2026 release found), it is a single ~4.6 MB Excel workbook on GOV.UK with 2,887 generic foods across ~13 sheets (Factors, Proximates, Inorganics, Vitamins, Vitamin fractions, fatty-acid fractions, phytosterols, organic acids), licensed under the Open Government Licence v3.0, so it can be converted to Postgres and shipped with the app with a one-line attribution. Nobody publishes an official JSON/SQL export, but three open-source importers (two in TypeScript) show the exact gotchas: 'Tr' means trace (store 0 + flag), 'N' means unknown (store null), carbohydrate and sugars are monosaccharide equivalents (divide by 1.05 for weight), fibre is given both as AOAC (what the UK 30 g target uses) and Englyst NSP, alcoholic drinks are per 100 ml, 33 foods lack energy, and code 13-669 is duplicated. For packaged/branded products use Open Food Facts v3 (barcode GET, ~172k UK-tagged products, ODbL, 15 req/min/IP, mandatory custom User-Agent) and cache locally; its Open Prices project is real but France-centric and its UK/GBP coverage is unverified, so it is not a Waitrose pricing source. USDA FoodData Central is CC0 with a free key and 1,000 req/hr, but its branded data is US-only and its generics differ from UK foods in fortification and salt; its main value here is cup-to-gram portion weights. Every commercial nutrition API (Edamam, Nutritionix, Spoonacular, FatSecret, CalorieNinjas) is US-centric and, crucially, Edamam's and Nutritionix's terms forbid caching/storing results, which defeats a design where the app owns a canonical ingredient table; Nutritionix no longer has a public free tier and starts at ~$499/month. For parsing, the practical stack is deterministic quantity/unit extraction with parse-ingredient 3.0.0 (TS, MIT, Sept 2026) plus a Claude structured-output call (Haiku 5.5 at $0.10/$0.50 per MTok, or Sonnet 5.5 at $2/$10) that normalises names and picks a CoFID match from a candidate list you retrieve with pg_trgm/pgvector, cached per normalised line so repeat ingredients cost nothing; the best Python parser (ingredient-parser-nlp 2.9.1, 95% sentence accuracy) would need a sidecar service. Recipe-calculated nutrition is typically within 10-15% of lab values for energy and macros but can be off 25-50% for saturated fat, sodium and micronutrients on individual dishes, so the UI should round kcal to the nearest 10, show an 'estimate' badge until every line is human-confirmed, and never display micronutrients to decimal places. UK targets to score against are well defined: 2,500/2,000 kcal, fibre 30 g (AOAC), free sugars <5% energy (~33 g/27 g), saturated fat <11% food energy (~31 g/24 g), salt <6 g, 5-a-day with the 80 g/30 g dried/150 ml juice-once/pulses-once rules, FOP traffic-light cut-offs per 100 g (fat 3/17.5, saturates 1.5/5, sugars 5/22.5, salt 0.3/1.5 g) and the 2004/05 Nutrient Profiling Model as a 'balance' score.

--- RECOMMENDATION ---
1) Canonical food table seeded from CoFID 2021 (OGL v3). At build time (or as a one-off script committed with a derived CSV/JSON plus the OGL attribution string), download the GOV.UK workbook and parse it in Node with SheetJS `xlsx` or `exceljs` (avoid `read-excel-file` in the server bundle — Turbopack tracing issue). Join sheets 1.3 Proximates, 1.4 Inorganics, 1.5 Vitamins (optionally vitamin fractions) on food code; store per-100 g values keyed by INFOODS tagname (KCALS, KJ, PROT, FAT, SATFOD, CHO, TOTSUG, AOACFIB, NA, plus FE, CA, VITD, FOLT, VITC, K if you want micronutrients). Rules: 'Tr' → 0 with is_trace flag; 'N' and blanks → NULL; store carbohydrate/sugars raw (monosaccharide eq.) AND a weight column = raw/1.05 with a flag; use AOAC fibre for the 30 g target; salt_g = NA_mg × 2.5/1000; mark group Q as per 100 ml; keep both 13-669 rows under synthetic codes; leave energy NULL for the 33 foods without kcal rather than deriving it. Tables: canonical_food(code, name, group, basis_100g|100ml, nutrients jsonb or wide columns, source='cofid-2021'), food_alias(alias, code, scope=global|household, created_by), food_portion(code, label e.g. 'tbsp'/'clove'/'slice'/'cup', grams, source, method). Seed food_portion from ExactCup (CC BY 4.0, 80+ items), USDA FDC foodPortions for common staples, and a hand-curated UK list (tsp 5 ml, tbsp 15 ml, egg 50 g, garlic clove 3 g, bacon rasher 25-35 g, bread slice 36-44 g). Add UK synonyms (aubergine/eggplant, coriander/cilantro, spring onion/scallion, caster sugar, double cream, rapeseed oil).

2) Parsing pipeline (TypeScript, runs in a Next.js route/server action): (a) normalise the line (lowercase, unicode fractions, strip bullets); (b) look up ingredient_line_cache by sha256(normalised line) → if hit, done (expect >70% hit rate after the first few weeks since households repeat ingredients); (c) run parse-ingredient 3.0.0 for quantity/quantity2/unit/description; (d) retrieve top-10 CoFID candidates for the description via Postgres pg_trgm similarity on canonical_food.name + food_alias (optionally pgvector embeddings later); (e) one Claude call per recipe (all lines batched) with structured outputs (output_config.format json_schema; TS zodOutputFormat) returning per line {qty, qty_max, unit, name_normalised, preparation, is_optional, cofid_code (enum from the supplied candidates or null), grams_estimate, confidence 0-1, note}. Use claude-haiku-5-5 by default ($0.10/$0.50 per MTok; ≈$0.0005/recipe), escalate to claude-sonnet-5-5 when confidence <0.6 or the recipe is non-English; put the system prompt + unit/alias guidance behind a cache_control breakpoint; use the Batch API (50% off) for bulk back-imports. (f) Convert to grams deterministically in code, not in the LLM: g = qty × grams_per_unit from food_portion, or qty × ml × density; grams only from the LLM when no table row exists, and flag it.

3) Human confirmation loop. Show each parsed line with its CoFID match and a confidence pill; one tap to accept, tap-to-search to fix. Lines <0.7 confidence or unmatched block the 'nutrition verified' badge; totals still display but carry an 'estimate' marker. Every accepted fix writes a household-scoped food_alias and updates ingredient_line_cache, so the system learns the family's vocabulary. Never auto-accept into totals without at least a glance-confirm.

4) Recipe nutrition = Σ(grams × per100g/100) over confirmed lines ÷ servings; store per-recipe and per-serving. Do not apply yield factors for per-serving totals; optionally apply a 'drained/absorbed oil' heuristic later. Prefer CoFID cooked entries when a line says 'cooked rice/pasta'. Recompute when servings or lines change; keep a nutrition_version so old plan weeks stay stable.

5) Packaged products: barcode or name → Open Food Facts v3 GET /api/v3/product/{barcode}?fields=product_name,brands,quantity,serving_size,nutriments,nutriscore_grade,countries_tags with a custom User-Agent 'MealPlanner/1.0 (contact@...)' and a token-bucket at ≤15 req/min; store the result in packaged_product (ODbL: fine for private household use; if the DB is ever published it must be ODbL, so keep OFF-derived rows in their own table). Treat nutriments.*_100g as per 100 g; fall back to a 'type the back-of-pack per-100 g panel' form (UK packs always carry it) or to the Waitrose product page nutrition table (covered by the Waitrose research stream). Do not use USDA Branded data; use FDC only for exotic generics missing from CoFID and for portion gram weights.

6) Scoring layer: per day and rolling week vs SACN targets (kcal by person, protein ≥0.75 g/kg, fibre 30 g, free sugars ≤5% energy, saturated fat ≤11% food energy, salt ≤6 g), 5-a-day counter with the 80 g/30 g dried/juice-once/pulses-once/no-potato rules, FOP traffic-light bands per 100 g per meal, and the 2004/05 Nutrient Profiling Model score (≥4 = 'less healthy') as the 'balance' signal for suggestions. Present honestly: round kcal to nearest 10 and macros to nearest gram, show '≈' and a tooltip 'database estimates are typically within 10-15% for energy; salt and micronutrients less certain', colour bands rather than decimals for micronutrients, and an amber 'estimate' badge whenever a line is unconfirmed, grams came from a density/LLM guess, or a packaged product lacks data.

7) Avoid as backbone: Edamam/Nutritionix (ToS forbid storing results; US-centric; Nutritionix ≥$499/mo), Spoonacular/FatSecret/CalorieNinjas (US data, small free tiers), Zestful (uncertain survival). Optional later: a Python sidecar running ingredient-parser-nlp 2.9.1 if the parse-ingredient + LLM combo proves weak on edge cases; and the FN-NBRI CoFID API only if you want a hosted lookup and accept its non-commercial-leaning terms.

########## recipe-import ########## findings: 48

--- SUMMARY ---
URL import is a solved problem for the majority of recipe sites because Google's rich-result programme has pushed almost every commercial recipe publisher to embed schema.org/Recipe JSON-LD; both the Python reference project hhursev/recipe-scrapers (v15.13.0, actively maintained) and a new TypeScript port, npm `recipe-scrapers` (v3.2.0, published 2026-10-03, Zod-validated, 14 site-specific + 291 schema.org-only hosts, with an `inspectRecipeEvidence` detect/uncertain/not-detected API) confirm this. Verified fixture data shows BBC Good Food, NYT Cooking, Waitrose, Serious Eats, Bon Appetit and AllRecipes all expose JSON-LD with ingredients, instructions, times and nutrition, but field shapes and nutrition strings are inconsistent ("25 grams fat" vs "17 g" vs "14 grams"), Waitrose and Jamie Oliver need HTML selectors for ingredients/method, and Bon Appetit's totalTime is unreliable. Nigella, Delicious magazine, Tesco Real Food and ottolenghi.co.uk have no site-specific scraper in either library and their JSON-LD presence is unverified. The real failure mode is not parsing but fetching: Serious Eats (Dotdash Meredith) has blocked server-side scraper traffic since early 2026 (Mealie issue, still broken Oct 2026), neither library bypasses bot protection, and Vercel functions egress from AWS datacenter IPs that Cloudflare-style protection targets; the robust answer is a client-side capture path (bookmarklet / PWA share target / paste-HTML / screenshot) that uses the user's own browser session, which also handles NYT Cooking's paywall. Claude structured outputs (`output_config.format`, GA on Haiku 5.5/Sonnet 5.5/Opus 5.5) make LLM fallback cheap: a Readability-cleaned page is ~2-5K tokens, so Haiku 5.5 ($0.10/$0.50 per MTok) costs roughly $0.001 per recipe and Sonnet 5.5 ($2/$10) roughly $0.02; images cost ceil(w/28)×ceil(h/28) tokens (≈1,300 for 1000×1000) and PDFs ~1,500-3,000 text tokens per page plus image tokens, with 32 MB / 600-page request limits and a 500 MB Files API. Video links are the weak spot: TikTok oEmbed returns the caption as `title` without a key, YouTube descriptions come from the Data API (1 quota unit) but captions require owner OAuth and unofficial transcript scrapers are blocked from cloud IPs, and Instagram's oEmbed needs App Review, returns no caption field, and the Basic Display API is sunset, so the honest UX is "paste the caption or screenshot the recipe card". Upload handling on Vercel must assume a 4.5 MB request body (official KB guides mid-2026) despite a changelog claiming 100 MB, so files should go browser→Vercel Blob (client `upload()` with multipart) and be fetched server-side; use `unpdf` (serverless PDF.js, Node 22+) rather than `pdf-parse` (canvas native dep). Copyright: UK law treats bare ingredient lists and basic steps as unprotectable, written method prose and photos can be literary/artistic works, the UK has had no private-copying exception since the 2015 BASCA judgment, so store structured data plus a link and keep any copied prose/photos private to the household rather than redistributable.

--- RECOMMENDATION ---
Build a tiered import pipeline with per-field provenance and confidence, and a mandatory review-before-save screen.

TIER 0 — Acquire. For a URL: server-side fetch from a Vercel Node route (Fluid compute, maxDuration 60-120 s, realistic browser headers, 10 s timeout, follow redirects, 2 MB HTML cap). Classify the response: 2xx with HTML → Tier 1; 401/403/429, Cloudflare/Akamai challenge markers ('Just a moment', cf-mitigated, captcha), or login/paywall interstitial → return {status:'blocked'} and offer the client-side capture path. Client-side capture = (a) a bookmarklet / PWA share-target that POSTs document.documentElement.outerHTML plus URL from the user's browser (inherits NYT login, bypasses datacenter-IP bot blocks, same approach Mealie documents), (b) a 'paste page text/HTML' box, (c) a screenshot upload (goes to Tier 3). Do not buy proxies or Firecrawl/Jina for v1; if later wanted, Jina Reader self-hosted (Apache-2.0) or Zyte pay-as-you-go are the cheapest add-ons.

TIER 1 — Structured data (deterministic, free). Run npm `recipe-scrapers` (3.x): first inspectRecipeEvidence(html,url) then scrapeRecipe(html,url,{safeParse:true,parseIngredients:true,fallbackYield:'4 servings'}). Confidence: 'detected' + non-empty times + yields → 0.9; 'uncertain'/partial → 0.6 and run Tier 2 to fill gaps; 'not-detected' → Tier 2 full extraction. Known quirks to code around: Waitrose and Jamie Oliver need HTML fallbacks for ingredients/method (the library has them), Bon Appetit totalTime unreliable, NYT ingredient groups depend on brittle class names, nutrition strings are inconsistent (treat as hint only; compute your own nutrition from parsed ingredients). Keep the raw JSON-LD and the normalised object in Postgres JSONB for re-processing.

TIER 2 — LLM extraction (Claude). Reduce the page first: Readability (via linkedom or jsdom) to get main content HTML, keep <ul>/<ol>/<table> intact, strip scripts/styles/nav, cap at ~30K tokens. Call Haiku 5.5 with output_config.format json_schema (schema: title, servings{amount,unit}, times{prep,cook,total minutes}, ingredientGroups[{name, items[{raw, quantity, unit, name, prep, optional}]}], steps[], equipment[], dietTags[], cuisine, sourceNotes, perFieldConfidence 0-1, extractionWarnings[]). Validate with Zod; if validation fails or self-reported confidence < 0.6 on ingredients/steps, retry once on Sonnet 5.5. Cost ≈ $0.001/recipe on Haiku, ≈ $0.02 on Sonnet. Same path handles pasted text and video captions.

TIER 3 — Uploads (photos, screenshots, PDFs). Browser → Vercel Blob via @vercel/blob/client upload() with multipart (avoids the 4.5 MB function body limit; Server Actions are 1 MB by default); server fetches from Blob. Images: auto-rotate via EXIF, downscale to ≤1,568 px long edge (or 2,576 px on high-res models), JPEG q≈85; send to Claude vision with the same JSON schema; use Sonnet 5.5 for handwriting/dense cookbook pages, Haiku 5.5 for clean screenshots (~$0.0003-$0.005 per image).
